# 角色与板型扩展设计

## 当前已实现

- `server/rules.js` 为浏览器可用的公共资料：角色名称、描述、阵营、职业类别、夜间行动阶段、立绘索引、角色奖，以及板型 ID、版本、人数与角色数量。
- 客户端角色说明与立绘、服务端身份分配、行动资格、屠边判定、阵营计分及荣誉名称复用这份资料。
- 唯一可选板型为 `classic12` v1：4 狼、预言家、女巫、猎人、白痴、4 平民。API 拒绝未实现的板型，不提供看似可用的新角色选项。
- 新房间持久化 `rulesetId` 与 `rulesetVersion`，同房间下一局沿用。旧房间兼容 classic12 v1。既有版本定义不得原地修改；未知规则版本拒绝开局，避免悄悄按新规则运行。
- 游戏执行仍由 `game.js` 的已验证规则控制。公共资料只用于描述和现有分支，不代表动态技能引擎；不能只添加元数据就启用新角色。

## 后续实现边界

增加角色时，先明确板型与规则，再补齐以下服务端能力及对应测试：

| 边界 | 必须定义的行为 |
| --- | --- |
| 开局初始化 | 每局角色资源与状态，下一局如何清空；玩家凭证不重建 |
| 夜间顺序 | 哪一阶段行动、跳过死亡角色、行动结束的依赖；同夜行动统一结算 |
| 行动校验 | 能否自选、重复目标、存活要求、次数限制、已提交不可更改 |
| 结算 | 护卫、解药、毒药等效果的优先级、抵消与冲突；禁止依赖请求到达顺序 |
| 死亡触发 | 区分狼刀、毒杀、放逐、枪击等原因；排队处理触发，全部处理完再判胜 |
| 信息权限 | 法官、本人、狼队、其他玩家、法官玩家预览分别能看什么 |
| 计分与荣誉 | 每种合法行为的加减分、封顶与结算幂等性；旧版结果按已结算数值累计 |
| 投票 | 无投票权、免死、额外票权、多轮投票必须显式建模；公开记录只在最终结算后生成 |

具体规则应形成版本化处理器，提供初始化、校验行动、结算阶段、死亡触发、玩家视图与计分接口；路由层只负责认证、并发过期校验和事务提交，React 不执行规则。待出现第二个真实板型时再抽取处理器，避免现在建立未经需求验证的插件框架。

## 推荐增量顺序

1. 守卫板：先确定连续守护、自守、守救同目标规则；把夜间效果改为统一结算，再上线新板型。
2. 狼王板：补齐死亡原因与触发队列，明确是否可在毒杀或自爆后发动技能。
3. 其他特殊角色：逐个补行动、可见性、胜负、积分及立绘；板型人数和阵营结构必须一起验证。

以上仅为扩展方案，当前未实现守卫、狼王或其他新角色。

## 投票记录的数据边界

建房时固定 `settings.publicVoteRecords`，默认开启；关闭与旧房间不生成逐人公开记录，不能中途开启回看。记录只包含日期、座位与昵称、投向、当时的投票资格、票数、放逐/平票/翻牌结果，不包含隐藏身份、档案或访问凭证。正在投票时，已提交的原始行动不返回给客户端；全部提交后仍需法官结算才生成快照。

投票记录写入现有私有 DATA_DIR，与房间一同持久化；开始下一局清空本局记录，计分历史单独保留。未来若增加警长票权、平票 PK 或白狼王自爆，应升级记录结构以区分轮次与票权，不能把新规则套用到当前一人一票的记录格式。

跨板型排名也需要版本设计：新增板型时，结算结果应保存板型 ID、规则版本和计分版本，提供按板型筛选；不同板型的表现分机会可能不同，不能直接假定跨板型积分代表相同强度。现有 classic12 已结算分值保持原样，不回算历史。
